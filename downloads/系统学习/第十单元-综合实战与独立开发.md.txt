# 第十单元：综合实战与独立开发

日期：2026-11-09

## 背景与目标

前九单元分别讲解语言、文件、Linux、类、网络、数据库、网页、执行器和身份部署。本单元把它们连接成一个可交付项目：为自己维护的机器建立资产清单，运行只读检查，追踪结果，并能备份恢复。

学习者应先独立实施，再对照参考项目。已有验证证明教材示例能运行，不证明你已掌握。最终验收不能只展示首页或一条成功日志，要能解释实现、修改需求和排查故障。

## 1. 将需求写成可检查行为

把下面作为自己的第一版需求，不先选框架：

| 用户动作 | 成功行为 | 失败行为 |
| --- | --- | --- |
| 管理员登记服务器 | 保存名称、地址、端口、环境并返回编号 | 错误类型/重复名称拒绝，旧数据不变 |
| 只读人员查看资产 | 分页读取 | 未登录拒绝；只读人员不能维护 |
| 操作员提交检查 | 返回任务编号，随后查状态 | 未知任务/非法资产/队列满明确拒绝 |
| 查询任务 | 看见目标快照、状态、结果和时间 | 不存在的编号返回错误 |
| 管理员追踪操作 | 看见资产变更、账户事件、任务提交者 | 其他角色直接调用接口也被拒绝 |
| 恢复历史数据 | 新文件中能登录、读取备份时的数据 | 不覆盖运行库，不重放未完成任务 |

明确第一版只做本机磁盘与 TCP 连接检查。TCP 成功只说明端口可建立连接，不证明应用正确；本机磁盘不是远程服务器磁盘。以后扩展 HTTP、SSH 等检查需要各自的授权、超时、结果与故障设计。

## 2. 分层，并画出一次请求

参考实现位于 [项目目录](项目/05-资产API/README.md)。按职责阅读：

- web/：表单、事件、请求、展示；不能决定服务端角色。
- secure_server.py：身份、来源、CSRF、角色检查后复用业务路由。
- server.py：路径、方法、JSON、错误码；也是前置课程无登录入口。
- storage.py：资产校验、SQL 和资产审计事务。
- jobs.py：任务入库、领取、状态事件与并发。
- task_worker.py：固定只读检查。
- auth.py：账户、密码派生、会话、身份事件和审计读取。
- backup.py 与 deploy/：恢复工具及运行配置。

独立画出 POST /api/jobs 的完整链：浏览器取值 → Cookie/Origin/CSRF → 角色 → 白名单 → 资产快照 → 事务入队 → 202 → 工作线程领取 → 子进程 → 结果事务 → GET 轮询。标注每个阶段可能返回或产生的错误。

参考解释：HTTP 请求线程只负责接收和查询；检查不在入队写事务中等待。任务状态在数据库中，页面只是观察者。一个共享 Store 对象保存路径，各操作分别建立连接。

## 3. 从空目录独立重建

不要一次抄完整项目。每阶段能运行再继续：

1. 写命令行脚本读取 JSON 清单，输出统计；用错误 JSON 和缺字段验证失败。
2. 增加参数、日志、退出码、超时和安全写文件；从不同工作目录运行。
3. 用 SQLite 保存资产，完成 CRUD 和审计事务；验证重复名称与回滚。
4. 用 HTTP 暴露接口；先用 Python 客户端调用，再写 HTML 表单。
5. 用普通 JavaScript 函数和回调展示结果，处理 400、409、网络断开。
6. 增加持久队列、两路工作线程、固定子进程和状态机。
7. 添加登录、角色和 CSRF；直接构造越权请求验证服务端。
8. 添加备份恢复，准备运行手册，在新文件恢复后重新登录。

遇到问题回到对应单元，不要同时引入新框架和新业务。代码组织可以不同，只要行为和安全边界可解释。

## 4. 一次完整操作演练

在独立练习库创建 admin、operator、viewer 三种账户，启动 secure_server.py。记录实际路径与端口，不记录密码、Cookie 或 CSRF。

管理员新增 web01，地址 127.0.0.1、端口为实验服务端口，环境 test。刷新页面确认保留，再修改端口并改回。重复创建同名应拒绝。记录请求方法、状态码和资产编号。

操作员登录，读取资产，提交该资产 TCP 检查和本机磁盘检查，等待结果。尝试修改资产应为 403。只读用户登录，尝试提交任务也应为 403。

管理员重新登录，读取审计。资产记录应含真实操作者，任务含提交者；审计不应包含密码派生值、Cookie、会话摘要或 CSRF。任务详情的事件应按入队、运行、终态排列。

备份，修改资产，再恢复到新库。在新端口启动恢复库，用密码重新登录，核对备份时的名称；旧会话不能使用，未完成任务不自动重放。最后停止练习服务并保留脱敏的演练记录。

## 5. 故障定位练习

| 人为制造的故障 | 应收集的证据 | 参考判断 |
| --- | --- | --- |
| 停止 Python 后刷新 | 浏览器网络错误、进程状态 | 先恢复服务，核对是否曾写入再重试 |
| 端口没有监听 | 任务 failed 和连接错误 | 与网页请求失败区分，平台仍可工作 |
| 错误 Origin/CSRF | HTTP 403，资产无变化 | 修正客户端契约，不放宽身份检查 |
| 第二实例使用同一数据库 | 启动错误、文件锁 | 停掉重复实例，不删除运行中锁文件 |
| 数据库写锁占用 | 503/工作线程日志 | 缩短事务、释放合法锁，核对未知结果 |
| 备份目标已存在 | 非零退出码，旧文件不变 | 换新文件名，不盲目覆盖历史 |
| 代理 502 | 上游监听与服务日志 | 先定位 Python，再检查代理地址 |

每个故障记录“观察 → 假设 → 检查 → 结论”，避免只写“重启后好了”。恢复后再次验证原功能，不能只看错误消失。

## 6. 独立扩展：增加资产备注

需求：资产增加可选备注 note，最多 200 个字符。先写验收：缺省为空，旧数据可读；新增/修改能保存；非文本或超长拒绝；网页按纯文本展示。

参考修改顺序：迁移新增默认空字符串列 → 校验允许 note 并填默认值 → INSERT/UPDATE 参数 → API 示例 → 表单与编辑回填 → 文本展示 → 成功、边界、旧库升级和特殊 HTML 文本检查。

不要只在网页增加输入框，数据库不会自动多出列；CREATE TABLE IF NOT EXISTS 不会升级旧表。不要把 note 拼进 SQL。提交前从旧库副本演练，确认升级不丢资产和审计。

第二个扩展练习是“任务结果导出”。先明确谁能导出、数量上限、字段和脱敏要求，再实现；不能把完整数据库或 sessions 表当作导出文件。

## 7. 版本管理与交付

用 Git 记录代码、教程、迁移和测试；忽略数据库、备份、私钥、日志和缓存。提交前检查 diff，避免把练习密码或生成文件带入提交。提交信息说明行为变化，验证记录写实际结果及限制。

交付至少包括：运行入口、依赖版本范围、账户创建、配置示例、启动停止、日志、接口契约、权限矩阵、任务白名单、备份恢复、已知限制。让另一位使用者仅按 README 完成启动，能发现缺失步骤。

## 8. 现有自动检查如何使用

在项目目录逐项运行，失败后先看对应场景，不以“其他测试通过”抵消失败：

```text
python check_project.py
python check_jobs.py
python check_auth.py
python check_backup.py
```

Linux 额外运行 `python3 check_lifecycle.py`；具备 Nginx、OpenSSL 时运行 `python3 check_tls.py --nginx /path/to/nginx`。浏览器依赖与 COURSE_AUTH_TEST 模式见项目 README。测试使用临时数据库，不应该指向实际工作数据。

这些检查分工不同：API 检查不能代替真实浏览器；浏览器成功不能证明数据库恢复；systemd 语法不能证明服务实际安装；证书验证不能通过关闭校验来“修复”。

## 9. 自我验收与参考答案

逐题用自己的代码解释：为什么继承 Handler？do_GET 谁调用？JSON 与 Python 字典何时转换？SQL 参数绑定解决什么？事务为什么包住审计？202 为何不是成功？超时后为何不自动重复提交？角色和 CSRF 有何不同？备份为何不只复制主文件？

参考要点依次是：复用请求解析并扩展行为；基类按方法约定调用；跨 HTTP 时编码/解码；分离值与 SQL 结构；变更与审计一起提交；任务只是接收；结果可能未知；授权与来源意图不同；运行库可能有 WAL 和并发变化。

通过标准：独立完成至少一个脚本和一次字段扩展；按角色矩阵验证平台；定位三类故障；完成新库恢复；能解释上述调用链。若仍需逐行照抄，回到相应单元练习，不以阅读完章节作为掌握证据。
