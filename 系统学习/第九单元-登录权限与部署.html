第九单元：登录、权限与部署

日期：2026-11-08

建设状态：登录、会话、服务端权限、CSRF 与身份审计已有课程和项目。部署备份补充课已提供运行手册与模板，备份恢复和实际进程生命周期已验证；Nginx/TLS 实际运行及系统服务安装仍未验证。

起点与目标

前置：HTTP 请求头、JSON、数据库事务、类继承，以及第七、八单元的页面与任务。先完成本章身份部分，再进入部署部分。最终要理解“谁登录了”“他被允许做什么”“如何证明操作来自这次登录”，并能搭建具有这些约束的运维平台。

为保留学习顺序，server.py 仍是第六至八单元无登录的本机实验入口；secure_server.py 是第九单元带身份检查的入口。它复用同一资产、任务和网页逻辑，但增加服务端身份检查。实际使用身份功能时必须启动 secure_server.py，不能只看到代码目录里有 auth.py 就认为 server.py 自动变安全。

1. 身份验证与授权分开理解

身份验证回答“你是谁”，授权回答“这个身份能做什么”。用户名密码正确只通过第一步，不意味着能执行所有操作。

角色 查看资产/任务/结果 提交固定巡检 增删改资产
viewer 允许 拒绝 拒绝
operator 允许 允许 拒绝
admin 允许 允许 允许

本课程按整个平台角色授权，不按资产分别授权。所有已登录用户能读取全部资产和任务结果。若需要“甲只能看甲的机器”，还必须增加资源归属及每次查询的过滤条件，不能仅依赖这个角色表。

角色来自服务器数据库，不接受浏览器提交的 role。管理员账户由掌握服务器文件权限的人通过本机命令创建；没有公开注册或网页提权入口。

练习：把浏览器中的角色提示改成 admin，可以修改资产吗？不能，服务端重新从会话关联的 users 读取角色。

2. 密码不能直接存进数据库

本项目使用 Python 标准库 PBKDF2-HMAC-SHA256，每个账户独立随机盐，迭代次数保存在用户记录中。盐不是密码，不要求保密；相同密码配不同盐会产生不同结果。随机盐防止相同密码产生相同存储值，较高计算成本增加离线猜测代价。

保存以下代码为 password_first.py：

import hashlib
import hmac
import secrets

password = "only-for-this-example"
salt = secrets.token_bytes(16)
saved = hashlib.pbkdf2_hmac("sha256", password.encode("utf-8"), salt, 600000)
entered = "only-for-this-example"
candidate = hashlib.pbkdf2_hmac("sha256", entered.encode("utf-8"), salt, 600000)
print(hmac.compare_digest(saved, candidate))

输出 True；把 entered 改成其他值，应为 False。不要在实际程序里硬编码密码，这里只用于理解比较过程。也不要将普通 SHA256(password) 当作密码存储方案。

auth.py 的 password_digest 负责派生值；set_user 生成盐并写入 users。用户名限制长度与字符，密码长度为 12—128 个字符。这里不声称密码长度本身可以替代安全部署。

实现使用 600000 次迭代作为本课程固定参数，升级时需要根据部署环境评估成本和算法选择。保存参数是为了以后能识别旧记录；当前还没有登录时自动重哈希升级。

练习：为何登录时不能再生成新盐？因为要用该用户原来保存的盐与参数重复计算，才能比较。新建或重置密码时才生成新盐。

3. Cookie 与会话：每次请求不必重新发送密码

登录成功后，服务器生成随机会话令牌，数据库只保存其 SHA256 摘要。令牌通过 Set-Cookie 交给浏览器；浏览器在后续请求中自动携带 Cookie，服务端取摘要查询 sessions，再关联 users。

这里对令牌用普通 SHA256，与密码派生不同：令牌本身是足够长的随机值，不是人类选择的低熵密码。原始令牌不进入日志、网页 JavaScript 或数据库字段。

会话有效期固定一小时，不随查询延长。每次成功登录替换同一用户的旧会话，因此一个用户只有一个有效登录。退出登录同时删除服务端会话并让浏览器 Cookie 到期；只删除浏览器显示状态是不够的。

Cookie 属性：HttpOnly 防止普通页面脚本直接读令牌；SameSite=Strict 限制跨站携带；Path=/ 限定路径；Max-Age=3600 设置浏览器寿命。配置公开地址为 HTTPS 时额外设置 Secure。本机 HTTP 实验不加 Secure，不能由此推导出 HTTP 适合远程传密码。

练习：复制退出前的 Cookie 再请求，会成功吗？不能，因为服务端记录已删除。清除网页文字但不撤销 sessions，则不具备这种效果。

4. CSRF：Cookie 会自动发送，所以写请求还需证明来源

浏览器自动发送 Cookie 给使用者带来方便，也意味着不能把“携带 Cookie”当作用户有意执行本次写操作的全部证据。

项目采用三个相互配合的检查：配置的 Origin 必须与写请求来源完全一致；登录要求 application/json 与 X-Requested-With 标记；登录后的写操作还必须携带与当前会话对应的 X-CSRF-Token。

CSRF 值由服务器随机生成，通过登录响应或 /api/me 返回，只留在页面变量中。app.js 的 request 在非 GET 请求中设置它。客户端传入另一个会话的 CSRF 值也不能通过。

Host 必须等于配置公开地址的主机与端口，以免任意域名指向本机时被当作合法访问。反向代理部署时应显式设置 --origin，并保持正确 Host；本项目不根据不可信 X-Forwarded-* 头猜测公开地址。

CSRF 不是授权：即使令牌正确，viewer 仍不能写入。它也不是 XSS 的补救：若页面脚本被攻击者控制，页面可读取 CSRF 值，所以仍要保留 textContent、固定静态路径与内容安全策略。

练习：Node 发起 POST 为何也要带 Origin 与 CSRF？因为本项目服务端对所有客户端执行同一契约。不要为“脚本方便”增加跳过验证的后门。

5. 沿登录调用链读源码

  1. 浏览器访问 /，SecureHandler 检查是否已有有效会话；没有则返回 login.html。
  2. login.js 读取输入，POST /api/login，密码只在请求体里。
  3. 服务端检查 Host、Origin、请求标记与字段。
  4. Auth.login 预先记录一次尝试，读取账户参数，计算密码派生值。
  5. 比较成功后再次核对账户未在计算期间变化，撤销旧会话，保存新会话及登录事件。
  6. Set-Cookie 写会话令牌，浏览器重新载入 /。
  7. 工作台请求 /api/me 取得用户名、角色与 CSRF，再加载资产与任务。

与第三、四单元联系：SecureHandler 继承 Handler，覆盖 dispatch，在复用原路由前执行权限判断。复用并不意味着省略父类逻辑；需要显式调用 Handler.dispatch(self)。

练习：如果把身份检查写在 Handler.dispatch(self) 后面会怎样？资产变更可能已经完成，随后才拒绝响应，保护顺序错误。

6. 尝试频率、错误响应与日志

同一用户名一分钟最多 5 次登录尝试，包括成功和失败。计数在数据库事务中先登记，再计算密码，避免并发请求绕过计数。未知用户名也执行一次派生运算，失败消息统一为“用户名或密码错误”。

这只是教学层的限速，不等于完整抗暴力破解：攻击者可更换用户名；用户名级限制也可能被用来暂时阻止他人登录。对外部署仍需要代理层速率和连接限制、监控、审计及适当身份系统。

auth_events 保存登录成功、失败、退出、本机账户更新；不记录密码、Cookie 或 CSRF。asset audit 增加 actor，jobs 增加 submitted_by，都由服务端身份赋值。原有记录迁移后使用 legacy-unknown，不伪造历史操作者。

角色不足/来源不符/CSRF 错误返回 403；未登录/会话过期返回 401；尝试过多返回 429。接口错误不要输出原始 SQL、密码派生值或请求头。

7. 创建账户并运行

进入项目目录，先创建自己的管理员；密码由 getpass 交互输入，不在命令行参数、仓库或 README 中保存：

python auth.py --db secure.sqlite3 --username myadmin --role admin
python secure_server.py --db secure.sqlite3 --port 8096

访问 http://127.0.0.1:8096/。创建账户与启动服务必须使用同一个数据库文件；建议实际运行传绝对路径。不要使用先前无登录服务的端口与它混淆。

另建 reader（viewer）和 runner（operator）账户，按角色矩阵分别尝试操作。同一用户名再次运行 auth.py 会重置密码和角色，并撤销其全部会话；这是本机管理操作，不是只在账户不存在时创建。

部署操作继续学习补充课。当前只监听回环地址。本机实验不需要对公网开放端口或设置数据库宽泛权限。

8. 验证不是只看能否登录

python check_auth.py

自动检查创建临时账户和数据库，不使用你的实际密码。它验证未登录拒绝、三种角色、CSRF/来源/Host、Cookie 属性、相同密码不同盐值、令牌摘要、身份审计、退出、重新登录撤销旧会话、过期、账户重置撤销和限速。

浏览器综合检查在第七单元的 Playwright 环境下运行。PowerShell：

$env:COURSE_AUTH_TEST = "1"
node check_browser.cjs
Remove-Item Env:COURSE_AUTH_TEST

Python 不在 PATH 时按项目 README 设置 COURSE_PYTHON。浏览器测试随机生成临时密码，经标准输入创建测试账户；不在命令行拼接密码。登录后执行真实资产维护与任务检查，再退出。旧的只读 Node 客户端未实现认证，访问安全入口返回 401 是预期行为，不能以此为由放开匿名读取。

9. 独立练习与参考答案

练习 A：画出密码、会话令牌、CSRF 三者去向。答案：密码进入服务端验证，不持久保存明文；会话令牌进入 HttpOnly Cookie，服务端存摘要；CSRF 进入页面内存并在写请求头中回传，服务端存在对应会话行。

练习 B：operator 直接构造 PUT /api/assets/1，并带正确 CSRF，结果如何？403，数据库不应改变。验证权限不能只测试网页按钮是否隐藏。

练习 C：管理员改密码后，旧页面仍显示资产，是不是旧会话仍有效？不一定。已有 DOM 可以保留旧数据；下一次请求应得到 401。页面显示与服务端会话状态必须分别检查。

练习 D：为“查看审计”设计权限，不急着写代码。参考：先定义只有 admin 可查询；在查询前检查角色；分页限制；不返回秘密；为 viewer/operator 的直接 HTTP 请求各加一个拒绝测试。当前尚没有完整审计浏览页面，不应宣称已交付该页面。

身份部分通过标准：能独立创建三种角色并验证矩阵；能说明 Cookie 与 CSRF 的差别；能定位一次 401 和一次 403；能解释继承入口的调用顺序；能验证旧会话撤销，而不只看退出按钮效果。

10. 继续学习部署与恢复

配置与秘密、最小权限、反向代理及 TLS、systemd 生命周期、日志、升级回退、SQLite 在线备份与恢复已整理为部署备份补充课。当前 --origin 和 Secure Cookie 不代表已经部署或验证 HTTPS；补充课列出了实际检查范围及未验证项。

尚未提供用户禁用/删除、多因素认证、资源级授权、账户恢复或审计保留策略。标准库 http.server 是教学服务，后续应明确它与生产服务器的边界。不能把本次身份验证通过扩展为“可以直接公网生产使用”。
