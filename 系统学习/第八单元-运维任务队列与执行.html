第八单元：运维任务队列与执行

日期：2026-11-08

起点与目标

前置：会调用 HTTP、使用 SQLite 事务，能看懂第七单元的回调。现在把“网页管理清单”推进到“网页提交巡检、后台执行、查询结果”。

学完要能解释：为什么返回 202 还不能说检查成功；两个工作线程如何避免领到同一任务；为什么超时需要处理子进程；服务重启后怎样处理未完成任务。项目继续在 05-资产API 中演进，不另复制一套难以同步的后端。

1. 请求不应该一直等检查结束

资产查询通常很快；检查可能要等待网络。如果 do_POST 里执行全部检查再返回，请求连接会一直占用，浏览器也不知道正在排队还是已经卡住。

改成两步：POST 保存任务，返回任务编号和 202；浏览器随后 GET 这个编号查看结果。202 表示接收，不表示检查成功。即使检查在浏览器收到响应前已经结束，这个接口仍表示异步接收。

流程是：页面 → POST /api/jobs → SQLite queued 记录 → 工作线程领取 → 独立子进程检查 → 结果写回 SQLite → 页面 GET 展示。浏览器没有直接启动操作系统命令。

练习：提交接口返回 202 后，TCP 连接被拒绝，最终状态应是什么？failed。接收成功与任务成功是两件不同的事。

2. 先用最小例子理解队列

把下面保存为 queue_first.py 并运行。这里只有一个消费者，不涉及线程。

import queue

pending = queue.Queue(maxsize=2)
pending.put_nowait("检查 web01")
pending.put_nowait("检查 web02")
try:
    pending.put_nowait("检查 web03")
except queue.Full:
    print("队列已满")

first = pending.get_nowait()
print(first)
pending.task_done()
second = pending.get_nowait()
print(second)
pending.task_done()

预期输出：队列已满、检查 web01、检查 web02。先放入先取出称为 FIFO。task_done 表示消费者处理完一项，它不会自动执行检查，也不会替你保存业务状态。

内存队列会随进程消失。本项目用 SQLite 中 state='queued' 的记录作为持久队列，按递增 id 领取。不要再建一份独立内存队列当作真实状态，否则要额外解决两份队列一致性。

练习：关闭程序后，queue.Queue 中的任务还能恢复吗？不能；SQLite 已提交的 queued 记录可以在下一次启动时重新领取。

3. 线程与进程各管什么

线程属于同一个进程，共享进程内存。子进程有独立执行环境，需要通过参数、标准输出等交换数据。本项目有两个长期工作线程，每次领取任务后启动一个短期 Python 子进程。

先运行这个独立线程示例：

import threading

ready = threading.Event()

def worker():
    ready.wait()
    print("工作线程开始检查")

thread = threading.Thread(target=worker)
thread.start()
print("主线程准备完成")
ready.set()
thread.join()
print("所有工作结束")

依次输出主线程准备完成、工作线程开始检查、所有工作结束。Event 用于通知，join 等待线程退出。不要把 target=worker 写成 target=worker()，后者会先在当前线程执行函数。

项目的 stop_event 用于停止领取新任务；关服务时先等已开始的有限时长检查结束。每个工作线程串行处理自己领取的任务，因此两个工作线程最多同时运行两个检查子进程。线程不是越多越好，数量要与机器、数据库和目标承受能力匹配。

练习：HTTP 同时来了 50 次提交，会立刻创建 50 个检查进程吗？不会，接收容量限制是 20，执行并发是 2。等待与运行之和超过容量后拒绝新的提交。

4. 状态机：允许哪些变化

状态 意义 下一状态
queued 已保存，等待领取 running
running 已领取，正在执行或保存结果 succeeded / failed / timed_out
succeeded 检查按约定成功 无
failed 检查失败，或重启时发现执行结果未知 无
timed_out 超过执行时限，已终止直接子进程 无

不要把所有结果都叫“完成”。连接拒绝是 failed；超过总时限是 timed_out。也不要让浏览器通过 PUT 把任务改成成功：状态只由执行器写入。

jobs 保存当前状态、输入快照、结果与时间；job_events 保存状态变化。领取和 running 事件在同一事务中，结束状态与结束事件也在同一事务中。时间由 SQLite CURRENT_TIMESTAMP 生成，按 UTC 理解；它不是前端本地时间。

练习：看到 running 能否断言网络请求仍在执行？不能，它还可能正在等待写入结果；服务异常中断也可能留下该状态。所以需要恢复策略。

5. 为什么两个线程不会重复领取

阅读 jobs.py 的 claim：BEGIN IMMEDIATE → 查最早 queued → 更新为 running → 插入 running 事件 → commit。这些步骤在同一写事务中完成。

如果改成先 SELECT，关闭连接，再 UPDATE，两个线程可能先后读到同一 queued 记录，然后各自执行。事务把“检查当前状态并改变状态”组合成一次原子操作。

数据库事务提交后才启动子进程，不能把远程检查放在写事务里等待，否则其他提交也会被锁住。固定线程数控制执行并发；事务控制领取正确性，它们不是相互替代的。

本项目对同一个数据库持有操作系统文件锁，不允许两个 JobEngine 同时运行。锁文件存在不代表服务仍在运行，真正的锁由操作系统持有；进程退出后锁会释放。不要在运行中删除或替换锁文件，也不要通过硬链接或不同文件路径启动第二套服务。

练习：把 capacity 改为 100 就能同时运行 100 个检查吗？不能，它改变接收容量；workers 决定最大执行数。

6. 白名单：让请求选择任务，不能提供命令

本项目的两个任务：

task 输入 实际行为
disk_usage asset_id 必须为 null 读取平台源码所在磁盘根目录容量
tcp_connect 已登记资产 id 读取该资产的 IPv4 和端口，建立连接后关闭

POST 必须恰好包含 task 和 asset_id。未知任务、多余 command 字段、布尔资产编号、缺字段都拒绝。TCP 暂不支持域名或 IPv6，避免把 DNS 解析时限混入第一版任务课程。资产可以登记域名，但执行这个检查时会明确报错。

执行器使用参数列表启动固定 task_worker.py，shell=False，不接收脚本路径或命令字符串。shell=False 只避免 shell 解释，并不能让任何程序参数天然安全；真正的限制来自任务、脚本、字段都由服务端控制。

这里的 TCP 是服务端向资产发起连接，不是 SSH 登录，不会读取远程磁盘，也不会执行远程命令。只能在自己有权检查的机器上练习。本地课程尚无账户权限，不能作为对外服务。

提交时把资产名称、地址、端口复制到 input_json。之后资产被编辑或删除，历史任务仍能说明自己检查了什么；不能在执行时再随意读取已经变化的新地址。

7. 超时与子进程输出

先单独运行以下代码，理解超时异常：

import subprocess
import sys

try:
    subprocess.run([sys.executable, "-c", "import time; time.sleep(5)"], timeout=0.1)
except subprocess.TimeoutExpired:
    print("直接子进程已因超时结束")

这个 -c 字符串是教师写死的演示，不来自网页。平台实际运行的是固定文件。run 等待进程，超时后终止并等待直接子进程，再抛 TimeoutExpired；进程创建本身不是硬实时可中断的，因此 3 秒不是绝对的端到端截止时间。

项目 TCP socket 自身限时 2 秒，外层检查进程限时 3 秒。正常连接超时可能先返回 failed；只有超过外层时限才归 timed_out。不要根据错误文字猜状态，应按执行边界分类。

worker 输出一小段 JSON；父进程根据退出码和 JSON 保存结果。当前白名单脚本输出有界，不启动孙进程。capture_output 会把输出放在内存里，不能原样扩展成任意大日志执行器；未来增加会生成大量输出的工具时，必须增加流式读取、容量限制及进程树清理。

练习：页面请求超时与任务执行超时相同吗？不同。页面超时后任务可能仍在运行，应查询编号或最近记录，不应自动重复提交。

8. 服务重启与异常处理

服务启动取得独占锁后：保留 queued，随后继续领取；将遗留 running 改为 failed，记录“服务中断，执行结果未知；未自动重试”。它不能保证上次检查完全没发生，所以不能说“重启后恰好执行一次”。

正常停机：停止接受新连接并收尾请求，停止领取，等待已执行检查结束，释放引擎锁。异常退出可能来不及记录结果；这正是恢复逻辑存在的原因。

数据库暂时不可用时，工作线程会记录错误类型并继续循环。若检查已执行、保存结果失败，记录可能留在 running，需恢复数据库后由管理员核对并重启恢复；本版没有心跳、租约、自动重派或结果重试日志。这是已知限制，不能隐藏成成功。

练习：为何不把所有遗留 running 直接改回 queued？因为将来任务可能有写操作，自动重试可能产生重复副作用。需要先设计幂等与人工核对流程。

9. 网页轮询：先查一次，再安排下一次

app.js 的 showJob 发 GET，收到 running/queued 才用 setTimeout 安排下一次，终态就停止。用这种方式避免 setInterval 在响应很慢时不断叠加请求。

用户切换查看另一个任务时，旧请求仍可能晚到。jobGeneration 每次加一，回调先比较代号，不匹配就丢弃旧响应，防止把旧任务结果盖到新任务上。网络失败停止轮询，并提供重新查看/刷新入口。

任务列表显示最近 20 条；任务详情按编号查询并显示输入快照、结果和事件。列表不是完整审计导出功能，后续综合阶段再考虑保留策略。

接口：GET /api/tasks 查询白名单；POST /api/jobs 提交；GET /api/jobs 最近记录；GET /api/jobs/编号 查询详情。已实现方法对任务详情做写操作返回 405。容量满返回 429，不代表已有任务丢失。

10. 实操与独立练习

启动 server.py，打开工作台。在任务区选本机磁盘并提交，核对 total_bytes、used_bytes、free_bytes。再登记一台 127.0.0.1、端口为当前 Python 服务端口的资产，按编号提交 TCP 检查，结果应 connected=true。只把端口改成自己确认未监听的本机端口，再提交，应得到 failed。

练习 A：画出提交、领取、执行、保存结果、查询的顺序；标出哪些步骤在 HTTP 线程、工作线程和子进程中。答案：提交/查询在 HTTP 线程，领取/启动/保存由工作线程负责，具体检查在子进程中。

练习 B：为新的任务“检查本机某个配置文件是否存在”列出改动点。答案：增加固定任务标识、服务端校验、固定允许路径、worker 分支、结果结构、前端选项、成功/缺文件/越权路径测试。不要直接接受网页传来的任意路径。

练习 C：为何任务输入使用资产快照？答案：资产编辑不能悄悄改变排队任务目标，历史记录也应可解释。若业务需要执行前重新授权或确认资产仍存在，应增加显式检查，而不是无意读取最新值。

练习 D：独立实现“只统计当前列表中失败任务数量”的普通循环。参考：遍历 items，state 等于 failed 时计数加一。timed_out 单独计数，不与 failed 混淆；最近 20 条的统计不能叫全部历史统计。

通过标准：能解释状态机和 202；能指出任务白名单校验位置；能说明为什么 claim 必须用事务；能完成真实磁盘与本机 TCP 检查；能区分请求超时、连接失败和进程超时；能解释恢复策略及其限制。
